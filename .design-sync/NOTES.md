# design-sync notes — Quire Ink admin UI

Repo-specific gotchas for anyone re-running this sync. Read before touching the config.

## What is synced, and what cannot be

- The synced design system is the **admin SPA** (`src/admin`): 130 React components, Tailwind v4,
  class-based `.dark`, deliberately monochrome neutral scale.
- The **public reader site is not syncable as components**. `src/web` contains no `.tsx` at all —
  every page is built as escaped HTML strings in `.ts` (`front-card.ts`), with CSS held in TS
  constants (`front.css.ts`, `prose.css.ts`). Claude Design renders React, so there is nothing to
  bind. Hùng chose (2026-08-01) to cover the reader look with a SECOND, tokens-only project rather
  than hand-writing React lookalikes, which would be a reimplementation and would rot on the first
  change to `front-card.ts`.

## Traps that cost real debugging time

- **`jsxImportSource: "hono/jsx"` in the root tsconfig silently breaks every preview.** esbuild
  picks a tsconfig by walking up from each file, so `.design-sync/previews/*.tsx` was reaching the
  root config and compiling to hono elements. React then refused them ("Objects are not valid as a
  React child") and every cell rendered BLANK with no build error. `.design-sync/tsconfig.json`
  exists solely to stop that walk. Do not delete it. The main bundle was never affected — its
  sources sit under `src/admin`, which has its own config.
- **There is no library `dist/` and no shipped `.d.ts`.** `node_modules/quireink` does not exist,
  so the converter must be given `--entry ./.design-sync/entry.tsx`. That barrel and the whole
  `componentSrcMap` are generated by `node .design-sync/gen-entry.mjs` — never hand-edit either.
- **Prop contracts had to be generated too.** With no `.d.ts` tree the converter emitted
  `[key: string]: unknown` for all 130 components, which is the exact thing the design agent codes
  against. `node .design-sync/gen-props.mjs` reads the real source types and writes `dtsPropsFor`.
  Re-run it whenever component props change.
- **`Image.extend({…})` / `Node.create({…})` are Tiptap schema, not components.** `CaptionedImage`
  and `Video` are PascalCase and pass a naive "is it a call expression" test, but putting them on
  the namespace fails the bundle export check. They are excluded in `gen-entry.mjs`
  (`NOT_COMPONENTS`).
- **A literal combining-mark range in a regex broke the whole bundle.** `foldAccents` in
  `src/utils.ts` spelled `[̀-ͯ]` with the actual characters; read as anything but UTF-8
  it becomes a reversed range and throws at parse time, killing every export. Fixed in the product
  source to use escapes, matching what `slugify` in the same file already did. Repo tests (1198)
  and typecheck pass with the change.
- **Read the component source, not just the props table, when authoring data.** `PostsTable` keys
  `views` by PATH (`/slug`) and `commentCounts` by bare slug. Keying both the same way renders a
  silent column of zeroes that nothing flags.

## Regenerating inputs

`cfg.buildCmd` is `bun run build:admin && bun .design-sync/gen-styles.ts`.

- `gen-styles.ts` writes `.design-sync/generated/` (gitignored): `admin.css` (compiled Tailwind
  plus the tokens), `fonts.css`, `tokens.css`. The admin's tokens and `@font-face` rules normally
  only exist at request time, built by `adminStyles()` in `src/web/admin/spa.ts` from the owner's
  saved settings; this calls the same functions against `DEFAULT_SETTINGS` so previews get the real
  palette, type scale and self-hosted faces instead of browser defaults.
- `cssEntry` is the CONCATENATION of compiled Tailwind + tokens, not an `@import` — only one file
  is copied to `_ds_bundle.css`, so an import would dangle.
- `tokensGlob` is unusable here: `copyTokens()` returns early unless `tokensPkg` is set, and
  `tokensPkg` resolves under `node_modules`.

## Provider chain

Previews wrap in `RouterProvider > AdminI18nProvider(lang="en") > ToastProvider > ThemeProvider`.
Without it ~40 components render empty: `Link`/`usePathname` need the router and most feature
components call `useAdminT`.

## Preview authoring

- `previews/_fixtures.ts` holds the shared data (posts, pages, comments, activity, bar rows)
  plus `SETTINGS`, which is the product's real `DEFAULT_SETTINGS` serialised by
  `gen-styles.ts`. Import from there rather than inventing another set of posts.
- **The compiled stylesheet only contains classes the admin already uses.** Tailwind is built
  with `@source "src/admin"`, so a preview (or any design the agent builds) that reaches for
  an unused utility renders unstyled with no error. Measured: `sm:grid-cols-4` is absent —
  only `grid-cols-1/2/3`, `md:grid-cols-4` and `lg:grid-cols-4` exist — so a stat row written
  with it silently collapsed to 2×2. `grep` the class in `_ds_bundle.css` before using it.
- Components that render NOTHING in some states are not broken previews, they are the
  component: `Trend` returns null when `prev` is missing/zero or the change rounds to 0%, and
  `StatTile` only draws its Trend when `value` is a NUMBER (a pre-formatted `"4,218"` silently
  drops `prev`). Compose those cases beside a value and label them, rather than shipping an
  empty cell.
- Icons are propless and fixed-size. A card showing the bare glyph reads as blank and trips
  `[RENDER_THIN]`; every icon preview shows name + three `currentColor` weights + the real row.

## Known render warns

None outstanding. The final build reports 130/130 previews rendering cleanly, 0 flagged.

## Still on the floor card (44 of 130)

Fully importable, with real `.d.ts` and `.prompt.md`; they just have no authored preview yet.
Authoring one on a later re-sync is additive and cheap — grades and previews carry forward.

Two groups are worth knowing about before picking any of them up:

- **The 13 route screens under `components/pages/`** (`Analytics`, `Comments`, `Content`,
  `Dashboard`, `Help`, `Log`, `Media`, `Newsletter`, `PageEditor`, `PostEditor`, `Settings`,
  `Trash`, `NotFound`) fetch on mount through `@/admin/api`. With no server they render a red
  `HTTP 404` box, which the render check counts as "rendered" but is worse than a floor card —
  it teaches the design agent a failure state. They cannot be fixed with props: the fetch is
  internal to the component. Either stub the API at bundle-build time, or drop them from
  `componentSrcMap` (they are routes, not design surface). **This is the first thing to decide
  on the next sync.**
- **`Editor`, `Toolbar`, `BubbleBar`, `TimeMachine`** need a live Tiptap editor instance or a
  revisions fetch, so they have no honest static composition.

## Re-sync risks

- `.design-sync/generated/` is gitignored, so a fresh clone MUST run `cfg.buildCmd` before the
  converter or `cssEntry` and `extraFonts` both dangle.
- `dtsPropsFor` and `componentSrcMap` are snapshots of the source. If components are added,
  renamed or re-propped, re-run `gen-entry.mjs` then `gen-props.mjs` before building, or the
  contracts silently describe the old API.
- The token values come from `DEFAULT_SETTINGS`. A real instance with a different palette, chrome
  font or type scale will not look like these cards; that is intended (the defaults are the
  product's own shipped look), but do not read the cards as "what Hùng's site looks like".
- Preview data is invented composition, not fixtures from the repo. There are no `examples/`,
  no docs-site MDX and no testing-library renders of the admin components to port from, so every
  preview was composed from the component source plus its props.
