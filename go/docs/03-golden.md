# Golden-file parity harness

The single highest risk in this project is that `marked` and `goldmark` render the
existing corpus differently and nobody notices until after cutover. This harness is a
**gate**, not a check: M1 does not pass until it is clean or every difference is
explicitly accepted in writing.

## What can differ, and why it matters differently

| Layer | Comparison | Strictness |
|---|---|---|
| Rendered article body | byte-for-byte after normalisation | **Strict.** A difference here means content changed |
| `<head>` metadata (title, description, OG, canonical, JSON-LD) | field-by-field | Strict on values, not on order or formatting |
| Page chrome (header, footer, nav, sidebars) | structural | Loose. The markup is being rewritten on purpose |
| Feeds and sitemaps | entry set and per-entry fields | Strict on values |
| Code blocks | token stream, not markup | Special case, see below |
| Search results | hand-written expectations | Excluded. Behaviour changes on purpose (parity exception #2) |
| OG images | not compared | Regenerated by a different renderer |

## Layout

```
go/golden/
  capture/            Go program: crawls Quire v1, writes references
  compare/            Go program: renders with Quire 2.0, diffs
  corpus/             hand-written markdown edge cases (see below)
  v1/                 captured reference output (git-tracked, it is the contract)
    body/<slug>.html      normalised article body only
    meta/<slug>.json      extracted head metadata
    feed.xml  sitemap.xml  llms.txt  ...
  accepted.yaml       every knowingly-accepted difference, with a reason
  report.html         generated diff report
```

`v1/` is committed. It is the frozen definition of "correct" and must not be
regenerated casually. Regenerating it is a reviewed change, because it silently moves
the goalposts.

## Capture

Runs against a local Quire v1 (`docker compose -f docker-compose.dev.yml up -d` plus
`npm run dev`) loaded with a **copy of production data**. Not seed data: the whole
point is to exercise the real corpus, including the posts with unusual markdown.

URLs crawled:

1. Every post slug and every page slug, live and draft (draft via `/preview/{slug}`)
2. Every category, tag and series page, and every pagination page of each
3. `/`, `/page/{n}` for all n
4. `/feed.xml`, `/sitemap.xml`, `/sitemaps.xml`, `/robots.txt`, `/llms.txt`,
   `/manifest.webmanifest`
5. `/api/md/{slug}` for every slug (markdown negotiation)
6. Each of the 6 locales and each of the 6 theme palettes for a representative subset,
   not the full cross product

### Normalisation before storing

Applied to captured HTML so the comparison is about content, not about Next:

- Remove `<script>` tags whose content matches Next's streaming payload (`self.__next_f`)
- Remove `<link rel="preload">` and chunk `<script src>` entries
- Remove React hydration attributes and comment markers
- Collapse insignificant whitespace **between block elements only**, never inside
  `<pre>`, `<code>`, or text nodes
- Sort `class` attribute tokens (Tailwind emits them in build order)

Everything else stays. In particular, do not "tidy" the HTML with a formatter; a
formatter would mask exactly the differences being hunted.

### Article body extraction

The strict comparison targets `#post-body` (posts) and the equivalent page container.
This is deliberate: the surrounding chrome is being rewritten and comparing it would
produce thousands of meaningless differences that hide the real ones.

## The corpus

Real posts do not exercise the edge cases where CommonMark implementations disagree.
`golden/corpus/` holds hand-written fixtures, each a small markdown file with an
expected-HTML sibling, covering at minimum:

- Nested lists at 3+ levels, mixed ordered and unordered
- A list item containing a fenced code block, and one containing a table
- Lazy continuation lines
- Setext vs ATX headings, headings with trailing `#`
- Emphasis adjacent to Vietnamese diacritics and to punctuation
  (`**lập**trình`, `*"quoted"*`, `a*b*c`)
- Intraword underscores (`snake_case_name`) which must NOT emphasise
- Raw HTML blocks and inline raw HTML (must be escaped, Invariant 5)
- `javascript:`, `data:`, `vbscript:` hrefs (must be dropped, Invariant 5)
- Autolinks, bare URLs, email addresses
- Reference-style links and images, including undefined references
- Footnote definitions before and after their reference, footnotes inside tables,
  duplicate footnote ids, unreferenced definitions
- GFM tables with alignment, escaped pipes, and inline code containing a pipe
- Task lists, including nested ones
- Fenced code with no language, an unknown language, and a language alias
- Hard breaks (two trailing spaces vs backslash)
- HTML entities and numeric character references
- A YouTube / Vimeo / TikTok URL alone in a paragraph (must become a video node)
- An image with a title attribute, and consecutive images that must group into a grid
- Very long lines, CRLF line endings, a BOM, a trailing-newline-free file

Around 60 fixtures. Each one that `goldmark` renders differently from `marked` is
either fixed with a goldmark extension or recorded in `accepted.yaml`.

## Code blocks: token comparison, not markup

Shiki and Chroma emit different HTML. Comparing markup would fail on every code block
for no useful reason.

Instead the comparison extracts, from both, the ordered sequence of
`(text, semantic-class)` pairs, where semantic class is mapped through a small table
(`keyword`, `string`, `comment`, `number`, `function`, `plain`, ...). A block passes if
the text concatenates back to the source and the semantic sequence matches within a
tolerance recorded per language.

Visual fidelity is then checked once per language by screenshot, not per block.

## `accepted.yaml`

```yaml
- id: goldmark-tight-list-paragraph
  scope: corpus/nested-list-mixed.md
  summary: >
    goldmark keeps a <p> inside a loose list item where marked strips it.
    goldmark follows CommonMark; marked does not.
  decision: accept
  impact: One extra <p> per loose list item. CSS already handles both.
  approved_by: Hung
  date: 2026-XX-XX
```

Empty at the start. Every entry is a deliberate decision with a named approver. If
this file grows past roughly 20 entries, that is a signal the parser swap is not going
well and the plan needs revisiting.

## Compare and report

`compare/` boots Quire 2.0 against the imported SQLite database, requests the same
URL set, applies the same normalisation, and diffs against `v1/`.

Output is `report.html`: a single page grouping differences by cause, with a
side-by-side view per case, sorted by number of affected URLs so the systematic
problems surface before the one-offs.

Exit code is non-zero when any unaccepted difference remains. This runs in CI on every
commit that touches `internal/render`.

## Running order

```
1. capture   (once, against v1 + production copy)          -> golden/v1/
2. import    (cmd/import-v1)                               -> quire.db
3. compare   (repeatedly, during M1)                       -> report.html
```

Step 1 is re-run only when the production corpus changes materially, and that re-run
is reviewed.
